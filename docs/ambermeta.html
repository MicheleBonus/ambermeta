AmberMeta Documentation

A provenance engine for AMBER molecular-dynamics workflows. It reads the files a run already produced — prmtop, mdin, mdout, mdcrd, inpcrd — reconstructs the staged protocol behind them, validates that the stages connect, and exports a machine-readable record for a methods section or a downstream pipeline.

v1.0.0 Python ≥ 3.8 · BUSL-1.1 CLI + GUI · offline

Overview #

AmberMeta answers the questions that are tedious to answer by hand about a finished AMBER simulation: What was actually run? In what order? Do the restarts line up? Is the topology hydrogen-mass-repartitioned? What were the ensemble, thermostat, barostat, and cutoff? Did the run finish? You point it at a directory — or a manifest — and it reconstructs the protocol and reports the provenance.

CapabilityWhat you get
Metadata extractionPer-file parsers for topology, input, output, trajectory, and restart files: atom/residue counts, box geometry, density, solvent model, HMR status, ensemble, thermostat/barostat, cutoff, SHAKE, completion, and streaming thermodynamics (temperature/pressure/density/energy, mean ± σ).
Protocol assemblyGroups loose files into ordered stages, detects numbered sequences (prod_0001 … prod_0050), infers each stage's role, and links the restart chain.
Continuity validationPer-file checks (atom-count agreement, box sanity) and cross-stage checks (timing gaps, restart→trajectory continuity), with configurable tolerances.
Canonical manifestsA tolerant reader (YAML / JSON / TOML / CSV, legacy aliases, several shapes) and a canonical writer (one deterministic on-disk form). The CLI and GUI write byte-identical manifests.
Reproducibility exportsA full protocol summary (JSON/YAML), a Materials-&-Methods-ready summary, and a per-stage statistics CSV.

Two interfaces sit on one shared core:

SurfaceUse it whenEntry point
CLIScripting, CI, SSH/cluster, headless batchambermeta <command>
GUIInteractively assembling or auditing a manifestambermeta gui
One engine, two faces. The CLI is the complete, headless interface — everything AmberMeta does is reachable without the GUI. The GUI is an optional, offline, localhost-only manifest editor that imports the same core through a single bridge module; it re-implements no logic. There is no separate TUI.

Installation #

AmberMeta targets Python 3.8+. The base install is dependency-light; optional features live behind extras.

$ python -m pip install -e .
ExtraPulls inEnables
(base)stdlib onlyAll parsers except NetCDF; JSON & CSV manifests; full CLI
netcdfnetCDF4, scipy, numpyNetCDF trajectory (.nc) and restart (.ncrst) parsing
guifastapi, uvicorn, websockets, python-multipart, pyyamlThe browser GUI (ambermeta gui)
yamlpyyamlYAML manifests
tomltomli (only on Python < 3.11)TOML manifests (3.11+ uses stdlib tomllib)
allnetcdf + gui + yaml + tomlThe full runtime feature set (not tests/dev)
 
$ python -m pip install -e ".[all]"     # all runtime features
$ python -m pip install -e ".[gui]"     # just the GUI
The GUI ships an offline bundle. The pre-built frontend lives under ambermeta/gui/static/ — no Node.js, no build step, and no CDN at runtime; it works on an air-gapped workstation. The gui extra only adds the Python web server.

Command-line interface #

The CLI is the complete, headless surface. Six commands sit under one entry point; global options (--log-level, --log-file, -q/--quiet) precede the subcommand.

CommandPurpose
planBuild & summarize a protocol; export reproducibility artifacts
initGenerate a manifest (template, or --auto from a directory)
validateValidate files without building a full protocol
infoPrint parsed metadata for a single file
guiLaunch the browser GUI
completionEmit a shell-completion script (bash / zsh / fish)

plan build + export

Build a protocol from a manifest, recursive discovery, or interactive prompts — and export artifacts. Pick exactly one mode: --manifest, --recursive, or --interactive.

Export flagOutput
--summary-path FILEFull protocol summary (JSON/YAML; --summary-format forces it)
--methods-summary-path FILEMaterials-&-Methods JSON: software, MD engine settings, system composition, restraints
--stats-csv FILEPer-stage statistics, one row per stage
Fault-tolerant by default. A missing/malformed/unreadable file is skipped, the error is recorded against its stage, and the run exits 0. --strict makes the first bad file a hard error (clean message, exit 1, no traceback). A stage keeps every file that did parse.

init bootstrap

--auto discovers files recursively and writes one stage per file-group stem — numbered sequences stay separate, not collapsed. Topology is classified automatically: an HMR-scaled prmtop becomes top-level hmr_prmtop, others global_prmtop. Use --dry-run to preview; --auto needs --force to overwrite.

validate & info inspect

validate reports OK / WARN / ERROR per file and exits 0/1 (--strict turns warnings into failures). info prints one file's parsed metadata as text, JSON, or YAML — the field names are the parser metadata fields.

The full flag list is generated from the parser and kept in sync by CI. See the CLI reference for every flag, with verbatim --help output.

Manifests #

A manifest is the durable, hand-editable description of a protocol. AmberMeta reads four formats and writes one canonical form.

FormatExtensionRequires
YAML.yaml, .ymlpyyaml
JSON.jsonstdlib
TOML.tomltomllib (3.11+) or tomli
CSV.csvstdlib

A manifest is either a list of stage dictionaries or a mapping of stage-name → dictionary. A stage recognizes exactly five file slots — prmtop, mdin, mdout, mdcrd, inpcrd — given either under a files mapping or as top-level keys.

# protocol.yaml
global_prmtop: systems/complex.prmtop
hmr_prmtop: systems/complex_hmr.prmtop
stages:
  - name: minimize
    stage_role: minimization
    mdin: mdin/min.in
    mdout: logs/min.out
  - name: prod1
    stage_role: production
    mdin: mdin/prod1.in
    mdout: logs/prod1.out
    mdcrd: traj/prod1.nc
    inpcrd: restarts/equil.rst7
    expected_gap_ps: 0.0
    gap_tolerance_ps: 0.1
Stage keyRequiredMeaning
nameyesUnique identifier; used for ordering and restart lookup
stage_rolenoInferred from content/path if omitted (always with an INFO note)
prmtop … inpcrdnoThe five file slots
gaps / expected_gap_ps / gap_tolerance_psnoExpected discontinuity before this stage
notesnoString or list → validation notes

Top-level settings controls validation: strict_validation (default true) toggles cross-stage continuity checks; allow_gaps (default false) records unconfigured gaps as info rather than warnings. Paths support ${VAR}/$VAR expansion unless disabled.

Tolerant in, canonical out. The reader accepts legacy aliases (stage→name, role→stage_role) and several shapes; the writer emits exactly one deterministic form. There is one on-disk representation to diff and review. Full schema: manifest reference.

Python API #

The same engine is a library. The supported import surface is everything re-exported from ambermeta.

The one thing to get right. A parser's parse() returns a wrapper that carries filename and warnings. The parsed metadata lives on .details. Field names are AMBER-flavored: hmr_active (not is_hmr), residue_composition (not residue_counts), temp_control/press_control/stage_role on mdin.
# Reconstruct a protocol from a directory...
from ambermeta import auto_discover, load_protocol_from_manifest

protocol = auto_discover("runs/", recursive=True, auto_detect_restarts=True)
print(len(protocol.stages), protocol.totals())
# 7 {'steps': 25000000.0, 'time_ps': 100000.0}

# ...or from a manifest
protocol = load_protocol_from_manifest("protocol.yaml", directory="runs/")

# Per-file parsing — note the .details accessor
from ambermeta.parsers import PrmtopParser
meta = PrmtopParser("system.prmtop").parse().details
print(meta.natom, meta.hmr_active, meta.solvent_type)

Core objects

ObjectKey members
SimulationProtocolstages; validate(cross_stage=True, allow_unexpected_gaps=False), totals() → {"steps","time_ps"}, to_dict(), to_methods_dict()
SimulationStagename, stage_role, the five file wrappers, expected_gap_ps/gap_tolerance_ps, validation, continuity, load_errors; degraded (property), summary(), to_dict()
ProtocolBuilderFluent: from_directory/from_manifest, with_grouping_rules, with_pattern_filter, with_stage_tolerance, auto_detect_restarts, add_stage, build()

Streaming thermodynamics live on mdout's stats (a ThermoStats): per-quantity StreamingStats via stats.temp_stats, stats.pressure_stats, stats.density_stats, … each exposing .mean and .stdev.

md = MdoutParser("prod.mdout").parse().details
print(md.finished_properly)            # True
print(md.stats.temp_stats.mean)        # 300.43200000000013
print(md.stats.temp_stats.stdev)       # 1.2504190252445306
Full signatures, every parser field, and the export structures are in the Python API reference.

Browser GUI #

A three-pane browser app — Files · Stages · Properties — for assembling and auditing a manifest. Single-user, localhost-only, fully offline.

$ ambermeta gui tests/data/amber/md_test_files     # opens http://127.0.0.1:8765
$ ambermeta gui runs/ --port 9000 --no-browser

A typical session: Discover auto-groups the directory into stages → drag files from Files onto stage slots (or use the picker) → edit a stage's name/role/gaps/notes in Properties → Link Restarts chains the inpcrd files → Validate reports issues with jump-to-issue → Save writes the canonical manifest, byte-identical to the CLI's.

Built to be safe on a workstation. The server binds 127.0.0.1, pins CORS to localhost, and confines every file path to the launch directory (resolved through symlinks; escapes get 403). State is server-authoritative — undo/redo and validation run server-side. It is not a multi-user service.

The frontend (React + TypeScript + Vite + Tailwind, drag-and-drop via dnd-kit) talks to a small REST API under /api you can drive directly:

AreaEndpoints
DocumentGET /api/document, /document/open, /document/save, /document/preview, /document/discover
StagesPOST /api/stages, PUT/DELETE /api/stages/{id}, /stages/reorder, /stages/bulk
StateGET/PUT /api/settings, POST /api/undo·/redo, /validate, /link-restarts, GET /api/sequences
FilesGET /api/files, /files/metadata, /files/related/{stem}
Full endpoint shapes, data models, and the UI tour are in the GUI guide.

Architecture #

AmberMeta is one engine with two faces. A single core — parsers, a manifest contract, protocol assembly, and a validation model — does all the work; the CLI and GUI are thin presentation layers over it. The same pipeline runs whether the entry point is ambermeta plan, load_protocol_from_manifest(), or a GUI Validate click:

directory or manifest
  → discovery / manifest   group files into stages, order them
  → parsing                Parser → .details (legacy *Metadata); failures → FileLoadError
  → assembly               build SimulationStage per group; infer role; link restarts
  → validation             per-stage + cross-stage continuity (notes, not exceptions)
  → export                 to_dict / to_methods_dict / stats CSV / canonical manifest
LayerResponsibility
Parsingparsers/ wrappers + legacy_extractors/ populate typed *Metadata on .details; mdout stats use Welford's online algorithm
ManifestTolerant reader (load_manifest, normalize_stage_keys) + canonical writer (write_manifest); STAGE_FILE_KINDS, CSV_COLUMNS
Assemblyauto_discover / ProtocolBuilder: group → sequence-detect → role-infer → link restarts
ValidationPer-stage (SimulationStage.validate) + cross-stage continuity; outcomes are INFO/WARNING notes
GUI bridgecore_bridge.py is the only GUI module importing the core; server-authoritative document; byte-identical manifests
Invariants worth remembering. (1) parse().details carries the metadata. (2) Tolerant reader, canonical writer. (3) One file group → one stage; sequences preserved, not collapsed. (4) Inference is always announced with an INFO note. (5) Failures are data (FileLoadError), not crashes — --strict opts into hard failure. (6) The GUI imports the core only through core_bridge.py.
The full internals walkthrough is in the architecture document.
