AmberMeta Documentation

A provenance engine for AMBER molecular-dynamics workflows. It reads the files a run already produced — prmtop, mdin, mdout, mdcrd, inpcrd — reconstructs the simulation behind them as a Simulation → Phase → Step document, validates that the steps actually connect, and exports a machine-readable record for a methods section or a downstream pipeline.

v1.1.0 Python ≥ 3.9 · BUSL-1.1 CLI + GUI · offline

Overview #

AmberMeta answers the questions that are tedious to answer by hand about a finished AMBER simulation: What was actually run? In what order? Do the restarts line up? Is any topology hydrogen-mass-repartitioned? What were the ensemble, thermostat, barostat, and cutoff? Did the run finish? Is a member of a numbered sequence missing? You point it at a directory — or a manifest — and it reconstructs the simulation and reports the provenance.

CapabilityWhat you get
Metadata extractionPer-file parsers for topology, input, output, trajectory, and restart files: atom/residue counts, box geometry, density, solvent model, HMR status, ensemble, thermostat/barostat, cutoff, SHAKE, completion, and streaming thermodynamics (temperature/pressure/density/energy, mean ± σ).
Simulation discoveryScans a directory into a Simulation draft: builds the topology pool, detects numbered sequences, infers each step's role (minimization/heating/equilibration/production) from content then path, and resolves the input-coordinate chain — all as explainable, undoable suggestions.
Continuity & sequence validationPer-file checks (atom-count agreement, box sanity) and whole-simulation checks (timing gaps between chained steps against a frame-interval-based tolerance, missing members of a numbered run), with configurable per-step tolerances.
Manifest format v2The one durable document: a topology pool, a starting structure, phases, and steps — read and written as JSON or YAML. The GUI and CLI share the same file, byte for byte.
Reproducibility exportsA full simulation/protocol summary (JSON/YAML), a Materials-&-Methods-ready summary, and a per-stage statistics CSV.

Two interfaces sit on one shared core:

SurfaceUse it whenEntry point
CLIScripting, CI, SSH/cluster, headless batchambermeta <command>
GUIInteractively assembling or auditing a manifestambermeta gui
One engine, two faces. The CLI is the complete, headless interface — everything AmberMeta does is reachable without the GUI. The GUI is an optional, offline, localhost-only manifest editor that imports the core through a single bridge module (ambermeta.gui.api.core_bridge); it re-implements no logic. There is no separate TUI.

The model #

v1.0 modeled a run as a flat Protocol → Stage (two levels; a "stage" was one run). v1.1 rebuilds this as three levels, matching how people actually think about a run:

LevelOwns
SimulationThe whole document. A topology pool (one or more prmtops, each labeled normal or hmr) and a single starting structure (the initial coordinates that feed the first run).
PhaseA named, role-bearing container (minimization / heating / equilibration / production) — a grouping/convenience level. It carries no files or topology of its own.
StepOne actual run (today's old "stage"). It binds one topology from the pool, names its mdin/mdout/mdcrd, and declares an explicit input-coordinate source.

Every step's starting coordinates resolve through input_coords: the FIRST step ← the Simulation's starting structure; every LATER step ← the previous step's output restart (the continuity chain); any step may override to an explicit path. This makes the old implicit "first stage uses initial_coordinates, later stages use the previous restart" rule an explicit, inspectable field instead of an assumption baked into ordering.

Continuity compares the previous step's output-restart end-time to the current step's input-coordinate time, with a frame-interval-based tolerance (not scaled to absolute elapsed time) — a healthy transition is never flagged. A missing member of a numbered sequence (e.g. prod_0001, prod_0002, prod_0004 → missing 0003) is a separate, first-class "sequence hole" finding, independent of whether any continuity gap was measured.

Both the CLI and GUI classify roles through the one shared function, ambermeta.roles.classify_role — canonical tokens are "minimization" | "heating" | "equilibration" | "production" | "", matched on word boundaries so minor.in never matches minimization.

What changed from v1. 2-level Protocol→Stage ⇒ 3-level Simulation→Phase→Step. Per-stage prmtop/global global_prmtop/hmr_prmtop ⇒ a Simulation-owned topology pool that steps bind by id. A flat initial_coordinates ⇒ a Simulation starting structure plus explicit per-step input_coords. New manifest format v2 — the only manifest format AmberMeta reads or writes. New CLI verbs discover and export. A rebuilt GUI (new canvas/inspector/suggestions tray).

discover draft (new)

Discover-as-draft: scans a directory into a Simulation draft using the same engine the GUI's Discover button calls (ambermeta.gui.api.core_bridge.discover_draft) — a topology pool, phases inferred by role, and steps with per-step topology binding and input-coordinate sources. Build a protocol from a manifest, recursive discovery, or interactive prompts — and export artifacts. Pick exactly one mode: --manifest, --recursive, or --interactive.

export convert (new)

Read a v2 manifest and re-emit it as canonical v2 — useful for converting between JSON and YAML, or for pretty-printing the whole document. -o/--output PATH (else prints JSON to stdout), --format {json,yaml} (else inferred from the output extension).

$ ambermeta export sim.json -o sim_v2.yaml --format yaml
Wrote v2 manifest: sim_v2.yaml (yaml)

Ids are carried through unchanged — export never renumbers anything. It does canonicalize: phases[].order and steps[].order are rewritten from document position, and keys come out in the canonical order write_simulation emits.

validate & info inspect

validate reports OK / WARN / ERROR per file and exits 0/1 (--strict turns warnings into failures). With --manifest PATH, it instead loads the whole Simulation through load_simulation and runs continuity/sequence-hole/suggestion checks — the same engine discover and the GUI's Validate panel use. --allow-gaps relaxes unexpected-gap findings without touching sequence holes. info prints one file's parsed metadata as text, JSON, or YAML — the field names are the parser metadata fields.

init bootstrap

init writes a static, commented v2 template manifest (topology pool, minimization + production phases, both input_coords sources shown) — it does not scan the directory; it's a starting point to hand-edit. Its only flags are -o/--output (default manifest.yaml) and --force, which overwrites an existing file without prompting. To build a manifest from a directory, use discover.

The full flag list is generated from the parser and kept in sync by CI. See the CLI reference for every flag, with verbatim --help output.

Manifests (v2) #

A manifest is the durable, hand-editable description of a Simulation: a topology pool, a starting structure, an ordered list of phases, and the steps inside them. This is manifest format v2 — the canonical, current shape:

version: 2
simulation:
  topologies:
    - id: top_wt
      path: wt.prmtop
      kind: normal          # "normal" | "hmr" (detected, overridable)
    - id: top_wt_hmr
      path: wt_hmr.prmtop
      kind: hmr
  starting_structure: wt.inpcrd
phases:
  - { id: ph_min,  name: Minimization, role: minimization, order: 0 }
  - { id: ph_prod, name: Production,    role: production,   order: 1 }
steps:
  - id: st_min
    name: minimize
    phase: ph_min
    order: 0
    topology: top_wt
    input_coords: { source: starting_structure }
    mdin: min.in
    mdout: min.out
  - id: st_prod_001
    name: prod_001
    phase: ph_prod
    order: 0
    topology: top_wt_hmr
    input_coords: { source: step, ref: st_min }   # or { source: path, path: "..." }
    mdin: prod_001.in
    mdout: prod_001.out
    mdcrd: prod_001.nc
    gaps: { expected: null, tolerance: null }
FieldMeaning
simulation.topologies[]The pool — every prmtop the Simulation uses, once, each an {id, path, kind}. Steps bind by id instead of each run carrying its own copy.
simulation.starting_structureThe initial coordinate file feeding the first step whose input_coords.source is starting_structure.
phases[]{id, name, role, order} — a role-bearing grouping; role is one of the canonical role tokens or empty.
steps[]{id, name, phase, order, topology, input_coords, mdin, mdout, mdcrd, notes, gaps} — one actual run.
input_coords.sourcestarting_structure · step (with ref: <step id>) · path (with path: "...") — the continuity anchor the validator walks.
gaps.expected / gaps.toleranceExpected inter-run gap and tolerance, in ps; both may be null.

v2 is read and written as JSON or YAML — nothing else. write_simulation emits those two; the reader picks YAML for a .yaml/.yml suffix and JSON otherwise. TOML and CSV are not manifest formats in either direction: handing a .toml or .csv path to any manifest reader fails with "AmberMeta reads and writes manifests as YAML or JSON only; TOML and CSV are not manifest formats." (The unrelated plan --stats-csv still writes a per-stage statistics CSV — that is a report, not a manifest.)

There is no v1 manifest

The old flat stages: manifest — global_prmtop/hmr_prmtop, initial_coordinates, one stage per run — is no longer readable. There is no reader for it and no migration path. Opening one is a hard error:

$ ambermeta export old.yaml

ERROR: Failed to load manifest: old.yaml is not a v2 manifest (no 'steps' key). Rebuild it with `ambermeta discover <dir> --write <path>`.

The fix is the one the message names: point discover at the directory the run lives in and let it rebuild the document as v2, then hand-edit anything it inferred wrongly. A file that does announce itself as v2 (version: 2, or a top-level simulation/phases key) but has lost its steps list gets a different message, telling you to restore the list rather than throw the file away.

One format in, the same format out. Every entry point — plan -m, export, validate --manifest, and the GUI's Open — reads v2 and only v2, and every writer emits v2. ambermeta init generates a fresh v2 template if you'd rather start clean. Full schema — every key, environment-variable expansion, role tokens: manifest reference.

Python API #

The same engine is a library, with two layers.

The one thing to get right. A parser's parse() returns a wrapper that carries filename and warnings. The parsed metadata lives on .details. Field names are AMBER-flavored: hmr_active (not is_hmr), residue_composition (not residue_counts), temp_control/press_control/stage_role on mdin.

Layer 1 — the new model: ambermeta.simulation

Plain dataclasses mirroring manifest v2. Not yet re-exported at the ambermeta top level — import it explicitly.

from ambermeta.simulation import load_simulation

sim = load_simulation("sim.yaml")   # v2 manifest, YAML or JSON
print(sim.topologies)
# -> [Topology(id='top_CH3L1_HUMAN_6NAG', path='CH3L1_HUMAN_6NAG.top', kind='normal')]
print(sim.starting_structure)
# -> CH3L1_HUMAN_6NAG.crd
for phase in sim.phases:
    print(phase.name, phase.role, [s.name for s in phase.steps])
# -> Production production ['ntp_prod_0001', 'ntp_prod_0002', 'ntp_prod_0003', 'ntp_prod_0004', 'ntp_prod_0005']

Browser GUI #

A rebuilt three-pane browser app — Files · Canvas · Inspector — for assembling and auditing a Simulation. Single-user, localhost-only, fully offline.

$ ambermeta gui tests/data/amber/md_test_files     # opens http://127.0.0.1:8765
$ ambermeta gui runs/ --port 9000 --no-browser
PaneRole
Files (left)A searchable file list; drag a file onto the topology pool, the starting-structure slot, a step's topology, or a step's mdin/mdout/mdcrd slot.
Canvas (center)A continuous vertical timeline — phases as sections, steps as cards showing their bound topology (▸) and input-coordinate source (◂); continuity arrows between steps (amber only where a real gap exists); missing-run ghosts for sequence holes; long numbered runs collapse. Drag to reorder steps within a phase, move a step across phases, or reorder phases.
Inspector (right)Peek + full-details/raw tabs for the selected file/step/phase, and assign actions. The Simulation, a phase, or nothing selected shows the suggestions tray instead.

A typical session: Discover scans the launch directory into a Simulation draft (topology pool, phases by role, chained steps) → drag files from Files onto canvas slots, or use the Inspector's assign actions → arrange steps/phases by dragging their grip handles → Validate reports continuity/sequence issues → Save writes the canonical v2 manifest, the same one the CLI's discover --write/export write.

Known limitation: the step/phase inline editors are still stubs. Selecting a step or phase highlights it and lets Validate jump to it, but the Inspector shows a placeholder rather than an editable form — rename a step, change its role, or set its gap tolerance via drag-and-drop assignment, the file-side Assign actions, the HTTP API, or by editing the manifest directly.

Every inferred thing — roles, the HMR topology, the starting structure, sequence holes, continuity gaps — is surfaced in the Suggestions tray as an explainable, undoable suggestion rather than applied silently. This is the draft-first design.

Built to be safe on a workstation. The server binds 127.0.0.1, pins CORS to localhost, and confines every file path to the launch directory (resolved through symlinks; escapes get 403). State is server-authoritative — a single document held server-side, every mutation returns the new document, undo/redo call the server. It is not a multi-user service.

Architecture #

AmberMeta is one engine with two faces. A single core — parsers, a role classifier, a manifest contract, simulation assembly, and a validation model — does all the work; the CLI and GUI are thin presentation layers over it. Two engine layers live side by side, deliberately:

LayerRole
ambermeta.simulationThe new Simulation → Phase → Step model: plain dataclasses plus load_simulation/write_simulation and the payload_to_simulation/simulation_to_payload round-trip. What discover, export, validate --manifest, plan -m, and every GUI operation build and hand around.
ambermeta.protocolThe retained flat SimulationProtocol/SimulationStage engine. Still does the actual file grouping, parsing orchestration, role inference, and continuity math — the v2 layer flattens into it rather than reimplementing validation. Also the whole path for plan --recursive and plan --interactive.
 
directory or manifest
  → discovery / manifest   group files into a topology pool + phases + steps (or flat stages)
  → parsing                Parser → .details (typed *Metadata); failures → FileLoadError
  → assembly                build SimulationStage per group; infer role; link restarts
  → validation              per-stage + cross-stage continuity, sequence-hole detection (notes, not exceptions)
  → export                 to_dict / to_methods_dict / stats CSV / v2 manifest

The validation model — how v2 reuses the old engine

The v2 validator does not reimplement continuity or per-stage checks; it flattens a Simulation back into the flat stage-dict shape ambermeta.protocol already knows how to validate, then calls the same discovery/validation pipeline the CLI's --recursive path uses. Concretely, core_bridge.validate_simulation(sim, settings, base_directory) flattens, runs auto_discover, then layers on two v2-specific suggestion kinds — missing_run (sequence holes) and continuity_gap (genuine, non-INFO continuity notes).

Manifest v2 and the single-format reader

def load_simulation(path: str, expand_env: bool = True) -> Simulation:
    """Load a Simulation from a v2 manifest file."""
    raw = _read_raw_manifest(path, expand_env=expand_env)
    if not isinstance(raw, dict) or "steps" not in raw:
        raise AmberMetaError(...)   # see below
    return payload_to_simulation(raw)

The gate is the steps key, not the version field — a hand-edited v2-shaped file without an explicit version: still loads. The two failure messages are deliberately different: a document that announces itself as v2 (version: 2, or a top-level simulation/phases key) but has no steps is a v2 manifest with a hole in it, so the error says to restore the list; anything else is told to rebuild with ambermeta discover <dir> --write <path>. Sending the first case off to rebuild from the directory would silently discard the phases and topology pool the file still has.

LayerResponsibility
Parsingparsers/ wrappers + legacy_extractors/ populate typed *Metadata on .details; mdout stats use Welford's online algorithm
ManifestReader (_read_raw_manifest → load_simulation, YAML/JSON) + canonical v2 writer (write_simulation, JSON/YAML) — one format, both directions
Assemblyauto_discover / ProtocolBuilder / discover_draft: group → sequence-detect → role-infer → link restarts

Invariants worth remembering. (1) parse().details carries the metadata. (2) One manifest format — load_simulation() accepts v2 JSON or YAML and nothing else; write_simulation() emits the same. (3) One role classifier (roles.classify_role), one continuity algorithm, one sequence-hole detector — shared verbatim by the CLI and the GUI. (4) Inference is always announced as an INFO note or suggestion, never a silent guess. (5) Failures are data (FileLoadError), not crashes — --strict opts into hard failure. (6) The GUI imports the core only through core_bridge.py.

Canonical role tokens

Both the GUI and CLI classify roles through the one shared function, ambermeta.roles.classify_role: "minimization" | "heating" | "equilibration" | "production" | "". Precedence: (1) authoritative content — imin=1 ⇒ minimization; (2) filename/path cues on word boundaries (min/minim/em, heat/warm/therm/anneal, equil/eq/nvt/npt, prod) — so minor.in never matches; (3) other content heuristics (restraints ⇒ equilibration; a temperature ramp ⇒ heating; a long run ⇒ production).

Exit codes & environment #

CodeMeaning
0Success (including a fault-tolerant plan/discover that skipped bad files, or a validate with no failing findings)
1Runtime failure — unreadable/missing input, parse/validation failure, nothing discovered, manifest not found/invalid, or a --strict hard stop
2Bad invocation — plan with no mode selected (--manifest/--recursive/--interactive); validate with neither files nor --manifest

Manifest paths (topology paths, starting_structure, mdin/mdout/mdcrd, an explicit input_coords.path) support ${VAR}/$VAR expansion by default; disable with --no-expand-env on plan. Undefined variables are left unchanged. export and validate --manifest load through load_simulation with expansion left on — there is no switch to disable it on that path.
